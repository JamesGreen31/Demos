High-Load d-ary Cuckoo Hashing Demo

What this demo shows

This hash table has a fixed number of buckets, and each bucket has only a few slots. Every key gets a small list of candidate buckets. If all candidates are full, the table tries moving other keys to make room. Near full load, those moves get longer and some inserts fail.

This is different from balls-into-bins load balancing, where bins are treated like unbounded counters. Here we model finite-capacity hash-table placement and relocation behavior as load approaches 1 − ε.

Key takeaway: simple random placement (or weak random eviction) starts failing earlier at high load, while structured relocation keeps inserts working longer. That is the practical point behind the 2025 high-load cuckoo hashing breakthrough.

Technical explanation + key terms

We simulate d-ary cuckoo hashing with two insertion policies: a naive random-walk eviction chain and a bubble-up-inspired augmenting-path search. The structured search usually finds shorter chains and keeps failure lower at high load.

  • N: number of buckets.
  • b: slots per bucket.
  • d: candidate buckets per key.
  • Load factor: inserted keys / (N × b).
  • Eviction chain: sequence of relocations needed to insert one key.
  • Failure: insertion that exceeds relocation step limit.
  • 1 − ε high load: operating very close to full capacity.

Reference: William Kuszmaul and Michael Mitzenmacher (2025), Efficient d-ary Cuckoo Hashing at High Load Factors by Bubbling Up (arXiv:2501.02312).

What the visualization game is showing

Think of each insertion as a small puzzle: can we place one more key using only its d candidate buckets? The chart and trace viewer show how hard that puzzle gets as the table fills.

  • Green/indigo bars show per-bucket occupancy from 0 to b slots.
  • The metrics show whether we are still inserting smoothly or hitting failures.
  • The eviction-chain viewer shows the bucket path visited during one insertion attempt (a short chain is good, long chains signal high pressure).

How to play

  • Set N, b, d, and K to choose table pressure.
  • Use Strategy to switch between naive random-walk eviction and bubble-up-inspired relocation.
  • Check the Strategy snapshot card to see both strategies compared on the same settings.
  • In Simulation Output, move the insertion trace slider to inspect a specific eviction chain.
  • Push K toward N × b (or slightly above) to observe longer chains and failures.

How to implement

  • Store a table as buckets[N][b], where each slot is empty or contains a key id.
  • For each key, compute d candidate buckets with seeded hash functions and mod by N.
  • Insertion: place directly if any candidate has free space; otherwise run relocation (random walk or augmenting-path search) with a max-step cutoff.
  • Track and display load factor, failures, average/max chain length, and throughput.
  • Use a seeded PRNG so changing only strategy keeps runs reproducible.
